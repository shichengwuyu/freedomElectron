# 第 8 章 浏览器端视频合成系统（ffmpeg.wasm）

> 对应简历亮点 7：基于 ffmpeg.wasm 构建 5 步流水线（归一化编码 → 分镜拼接 → 混音 → 字幕烧录 → 输出 MP4），针对 wasm 内存上限做分段处理，实现客户端零成本合成。

## 8.1 为什么在浏览器端合成（决策复盘）

| 维度 | 浏览器端 ffmpeg.wasm | 服务端转码集群 |
|---|---|---|
| 边际成本 | **零**（用用户算力） | CPU/GPU 大户，SaaS 最贵固定成本之一 |
| 带宽/隐私 | 素材已在本地/Storage，不传原始素材 | 需下载素材、上传成片 |
| 性能上限 | 受设备与 wasm 约束（见 8.2） | 高 |
| 离线可用 | 是 | 否 |
| 一致性 | 浏览器差异需兜底 | 环境可控 |

结论：主力路径浏览器端，服务端合成保留为"付费长视频/低端设备"的升级路径——**这个取舍本身就是面试加分点：不是技术炫技，是成本结构决定架构**。

## 8.2 技术底座：ffmpeg.wasm 的运行模型

理解四个约束，才理解所有设计：

1. **wasm32 线性内存**：单实例通常上限 2GB（4GB 寻址的一半预留给栈/堆元数据），**所有输入、输出、中间文件都活在这 2GB 里**——这是"分段处理"的根本原因；
2. **虚拟文件系统（MEMFS）**：ffmpeg.wasm 没有真文件系统，`-i input.mp4` 读的是写入内存的虚拟文件——素材越大数据越早爆；
3. **必须跑在 Worker**：主线程跑 wasm 会冻结 UI；Worker 化后主线程只收发消息；
4. **SharedArrayBuffer 需要 COOP/COEP 响应头**（多线程版）：部署时配 `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`——**站点所有跨域资源（Storage 图片等）必须带 CORS**，这是部署时踩过的经典坑。

```
主线程（React）                    Worker（ffmpeg.wasm）
────────────────                  ────────────────────
compositor.pipeline.ts            ffmpeg.worker.ts
  编排 5 步流水线                    加载 core（约 25MB，首次缓存）
  fetch 素材 → ArrayBuffer  ──cmd──▶ 写入 MEMFS → exec(cmd)
  接收进度/日志             ◀─msg──  progress 事件（time/duration）
  写 OPFS 中间产物                   读取结果 → transferable 回传
  最终 MP4 → Storage 上传
```

## 8.3 五步流水线详解

前置：所有素材按分镜顺序组织成清单 `TimelineSpec`（节点 id → 素材 URL/时长/音轨/字幕）。

**Step 1 归一化编码**——所有输入统一成相同参数的中间格式：

```bash
ffmpeg -i seg_03.mp4 \
  -vf "scale=1920:1080:force_original_aspect_ratio=decrease,pad=1920:1080:(ow-iw)/2:(oh-ih)/2,fps=30" \
  -c:v libx264 -preset veryfast -crf 20 -pix_fmt yuv420p -an \
  -c:a aac -ar 44100 -ac 2 norm_03.mp4
```

为什么必须先归一化：不同生成任务产出的片段分辨率/帧率/编码参数不一，直接 concat 会出现花屏、时间错乱或播放器兼容性问题。归一化后（统一 1080p30 / H.264 yuv420p / AAC 44.1kHz）后续拼接才可靠。**缩放在这一步一次性完成**——后续步骤不再持有大尺寸帧，是内存优化的第一环。

**Step 2 分镜拼接**：

```bash
# concat 列表文件（归一化后 concat demuxer 才可靠：同参数流直接拼容器，无需重编码）
ffmpeg -f concat -safe 0 -i list.txt -c copy merged.mp4
```

`-c copy` 不重编码，秒级完成且几乎不耗内存——归一化投资在这里收回。

**Step 3 混音**：配音轨 + BGM 轨混合，BGM 自动压低（sidechainduck），时长对齐视频：

```bash
ffmpeg -i merged.mp4 -i dubbing.mp3 -i bgm.mp3 -filter_complex \
  "[2:a]volume=0.25[bgm];[1:a][bgm]amix=inputs=2:duration=first,afade=t=out:st=595:d=5[a]" \
  -map 0:v -map "[a]" -c:v copy -c:a aac with_audio.mp4
```

**Step 4 字幕烧录**：台词字幕按分镜时间轴生成 SRT，subtitles 滤镜烧进画面：

```bash
ffmpeg -i with_audio.mp4 -vf "subtitles=subs.srt:force_style='FontName=Noto Sans SC,FontSize=16,Outline=1'" \
  -c:v libx264 -preset veryfast -crf 20 -c:a copy final_subbed.mp4
```

**Step 5 输出封装**：faststart 前置 moov（边下边播的关键）：

```bash
ffmpeg -i final_subbed.mp4 -c copy -movflags +faststart output.mp4
```

## 8.4 内存分段策略（本章核心）

问题量化：10 分钟 1080p30 成片，最终 MP4 约 200~400MB；如果五步串行且每步都把上一步产物整体留在 MEMFS，峰值 = 输入 + 全部中间产物 + 输出 ≈ 轻松超过 2GB → **wasm OOM，页面崩溃**。

四段策略：

1. **用完即删（MEMFS 纪律）**：每步开始前只挂载本步所需文件，结束后 `ffmpeg.FS('unlink', ...)` 立即删除输入与未需要的中间产物——任何时刻 MEMFS 里最多 2~3 个文件；
2. **归并式分批拼接**：Step 2 不是一次 concat 全部分镜，而是每次 4~6 段一批，批产物 `part_k.mp4` 写入 **OPFS**（浏览器持久文件系统，不在 wasm 内存里），下一批从 OPFS 读回——内存峰值从 O(全片) 降到 O(单批)；
3. **OPFS 作二级存储**：`navigator.storage.getDirectory()` 提供源私有的持久文件系统，可存数百 MB 中间产物且断点续跑（8.6）；MEMFS ↔ OPFS 之间用流式 copy，不整体加载；
4. **内存水位监控**：`performance.memory`（Chrome）+ ffmpeg core 的内存水位估算，超 75% 时自动切更小批次（4→2 段）并降低中间码率（crf 20→23）。

```ts
// 分批归并的骨架
async function mergeInBatches(segments: string[]): Promise<string> {
  let batchNo = 0
  let frontier: string[] = segments            // 待归并的片段（OPFS 里的 key）
  while (frontier.length > 1) {
    const next: string[] = []
    for (let i = 0; i < frontier.length; i += BATCH) {          // BATCH = 4~6，动态可降
      const group = frontier.slice(i, i + BATCH)
      const out = `part_${batchNo++}.mp4`
      await runInMemFs(group, out)             // 在 MEMFS 内 concat 一批
      await memfsToOpfs(out, out)              // 产物挪进 OPFS，MEMFS 删干净
      group.forEach(deleteFromOpfs)            // 已归并的原料清理
      next.push(out)
    }
    frontier = next                            // 4→1 层层归并，类似外排序
  }
  return frontier[0]
}
```

这是**外排序思想在浏览器里的应用**：把"放不下"的数据用磁盘（OPFS）分批消化，每批在内存里完成——面试可以直接这么类比，很出彩。

## 8.5 进度反馈与时长加权

ffmpeg.wasm 的 `progress` 回调给 `time/duration` 比值。五步耗时特征不同（Step 1/4 重编码占大头，Step 2/5 秒级），总进度按**预估耗时加权**：

```ts
const WEIGHTS = [0.35, 0.05, 0.15, 0.35, 0.10]   // 归一化/拼接/混音/字幕/封装
// 总进度 = Σ(已完成步权重) + 当前步权重 × 当前步内部进度
```

日志也回传（`log` 事件），失败时从 ffmpeg stderr 提取人话原因（如 `Invalid data found` → 定位到具体素材）。

## 8.6 失败恢复与断点续跑

- **step 边界即检查点**：每步产物持久化到 OPFS 并记录 `stage` 到 IndexedDB；失败重试从失败 step 开始，不从头来；
- **素材级定位**：预检阶段（Step 0）逐个探测素材可读性（时长/编码），坏素材提前拦截并标注到具体分镜节点——避免跑 8 分钟后在 Step 2 崩掉；
- **页面中断**：OPFS 里的中间产物跨页面存活，重开页面提示"检测到未完成合成，从 62%（字幕烧录）继续"；
- **存储配额**：`navigator.storage.persist()` 申请持久化配额；合成完成后清理全部中间产物。

## 8.7 时间轴与对齐

合成可靠的前提是**时间轴先算清楚**（纯 TS 计算，不碰 ffmpeg）：

1. 每个分镜的目标时长 = max(镜头设定时长, 配音实际时长)——配音没配画面就断；
2. 分镜累加得到全局时间轴 → 字幕 SRT 的时间戳、BGM 淡出点全部由它推导；
3. 若配音超长：按节奏微调该分镜视频速度（`setpts`，±10% 内无感）而不是截断台词；
4. 音画对齐验证：合成前 dry-run 断言 `Σ分镜时长 == 视频流时长`，误差 > 100ms 拒绝进入 Step 2。

## 8.8 性能数据（面试口径，替换成你的实测值）

- 1080p30、5 分钟、20 个分镜：内存峰值 ~900MB，总耗时 6~9 分钟（M 系芯片）/ 12~18 分钟（中端 Windows）；
- 分批策略收益：关闭分批（全量 concat）在 6 分钟片长即 OOM；开启后 10 分钟+ 稳定；
- 首次加载 core ~25MB（缓存后续零开销），COOP/COEP 配置后多线程版提速约 2~3 倍。

## 8.9 面试考点提炼

1. **"为什么浏览器端合成？"** → 成本结构决定架构（8.1），主动承认上限并给出服务端升级路径；
2. **"五步流水线每步干嘛？"** → 8.3 五条命令 + 每步的"为什么"：归一化保证 concat 可靠、`-c copy` 收回投资、faststart 便于流播；
3. **"内存上限怎么解决？"** → 8.4 四段策略，金句："外排序思想——OPFS 当磁盘，MEMFS 当内存，归并式分批"；
4. **"COOP/COEP 是什么、踩过什么坑？"** → 8.2 第 4 条：跨域隔离头一配，全站资源都要 CORS——部署踩坑故事的最佳素材；
5. **"失败恢复？"** → step 检查点 + OPFS 断点 + Step 0 素材预检（8.6）；
6. **"音画不同步怎么办？"** → 8.7：时间轴先行 + dry-run 断言，ffmpeg 只做"执行者"不做"决策者"。
