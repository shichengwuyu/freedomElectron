# 第 5 章 3D 导演台系统

> 对应简历亮点 4：通过 iframe 加载独立 Three.js 应用，使用 postMessage 实现跨应用通信，确保功能模块的解耦与独立性。

## 5.1 为什么是 iframe，而不是把 Three.js 集成进主应用

| 维度 | iframe 独立应用 | 直接集成进主应用 |
|---|---|---|
| 故障隔离 | 3D 崩溃/死循环只挂 iframe，画布无恙 | WebGL 上下文丢失、render loop 卡顿直接影响画布主线程 |
| 体积 | 主应用首屏不含 Three.js（约 600KB+ gzip 前），进导演台才加载 | 打进主 bundle，所有用户付出体积代价 |
| 独立迭代 | 3D 应用单独仓库/单独构建/单独发版，主应用通过 URL 接入 | 每次改 3D 都要全量发版 |
| WebGL 上下文 | 各自独立上下文 | 与画布可能的 canvas 渲染竞争上下文数量上限 |
| 通信成本 | postMessage 序列化 | 直接函数调用 |

四个收益换一个代价（通信要序列化），权衡成立的原因：**导演台与画布的交互频率是低频指令级**（加载场景、设置机位、回传状态），不是高频数据级，postMessage 的序列化开销可忽略。

## 5.2 3D 应用（iframe 内部）架构速写

```
director3d-app/                    # 独立构建的 Three.js 应用
├── src/
│   ├── main.ts                    # 入口：建立渲染循环 + 监听 message
│   ├── scene/
│   │   ├── SceneManager.ts        # 场景图管理：地面、天空盒、角色占位
│   │   ├── PanoramaLoader.ts      # 全景图 → 天空盒纹理（equirectangular）
│   │   └── CharacterLoader.ts     # 角色立绘 → 场景内 billboard/模型
│   ├── camera/
│   │   ├── CameraRig.ts           # 机位：位置/朝向/FOV/运镜关键帧
│   │   └── Timeline.ts            # 镜头时间轴：关键帧插值（lerp/slerp）
│   ├── protocol/
│   │   ├── types.ts               # 与宿主共享的消息类型定义
│   │   └── bridge.ts              # postMessage 收发、requestId 管理
│   └── loader/                    # glTF/纹理加载器，带进度上报
└── vite.config.ts                 # 独立构建，产物部署到独立路径/域名
```

关键点：**`protocol/types.ts` 是两个应用共享的独立包**（monorepo 里抽成 `packages/protocol`），宿主和 3D 应用 import 同一份类型定义——消息类型改了，两边编译期同时报错，这是跨 iframe 通信不腐化的关键。

## 5.3 宿主侧：iframe 生命周期管理

```ts
class Director3DHost {
  private iframe: HTMLIFrameElement | null = null
  private state: 'idle' | 'loading' | 'ready' | 'error' = 'idle'
  private pending = new Map<string, Deferred>()   // requestId → 待 resolve 的调用

  async mount(container: HTMLElement) {
    // ① 创建 iframe：sandbox 收权 + allow 脚本
    this.iframe = document.createElement('iframe')
    this.iframe.sandbox.add('allow-scripts', 'allow-same-origin')  // 最小权限
    this.iframe.src = DIRECTOR_3D_URL                              // 独立部署地址
    container.appendChild(this.iframe)
    // ② 等 3D 应用 ready 握手（带超时）
    await this.waitReady(15_000)     // 超时 → state='error'，UI 显示重试按钮
  }

  /** 预热：主应用进入画布时就挂一个隐藏 iframe，用户点开导演台零等待 */
  static preload() {
    const ghost = document.createElement('iframe')
    ghost.src = DIRECTOR_3D_URL
    ghost.style.cssText = 'width:0;height:0;border:0;position:absolute'
    document.body.appendChild(ghost)
  }

  /** RPC：基于 postMessage 的请求-响应封装（详见 5.4） */
  call<T>(type: MessageType, payload: unknown): Promise<T> {
    const requestId = crypto.randomUUID()
    const deferred = new Deferred<T>()
    this.pending.set(requestId, deferred)
    this.iframe!.contentWindow!.postMessage(
      { source: 'canvas-host', type, payload, requestId },
      DIRECTOR_3D_ORIGIN,                          // ★ 不用 '*'
    )
    setTimeout(() => {                              // 超时兜底，防内存泄漏
      if (this.pending.delete(requestId)) deferred.reject(new Error('timeout'))
    }, 30_000)
    return deferred.promise
  }
}
```

三个生命周期细节：

1. **预热**（`preload`）：用户画布操作期间就静默加载 3D 应用，点开时已 ready——这是"iframe 慢"感知的主要解法；
2. **ready 握手**：3D 应用初始化完成后主动发 `{type:'ready', payload:{version}}`，宿主收到才置 ready；版本字段用于兼容性检查；
3. **销毁**：React 卸载时移除 iframe 并清空 pending Map（否则 Deferred 泄漏）；3D 应用监听 `pagehide` 释放 GPU 资源。

## 5.4 postMessage 通信协议

### 5.4.1 消息信封

```ts
// packages/protocol/types.ts —— 宿主与 3D 应用共享
interface Envelope<T = unknown> {
  source: 'canvas-host' | 'director3d'   // ★ 发送方身份，接收端第一道过滤
  type: MessageType
  payload: T
  requestId?: string                     // 有 = 请求；无 = 单向通知/回传
  timestamp: number
}

type MessageType =
  // 宿主 → 3D
  | 'scene:load'          // { panoramaUrl, characters: [{url, position}] }
  | 'scene:clear'
  | 'camera:set'          // { position, lookAt, fov }
  | 'camera:playTimeline' // { keyframes: [{t, position, lookAt, fov}] }
  // 3D → 宿主
  | 'ready'               // { version }
  | 'scene:loaded'        // { sceneId, stats: {objects, textures} }
  | 'camera:snapshot'     // { cameraState }  ← 用户在 3D 里调完机位回传
  | 'load:progress'       // { ratio }        ← 资源加载进度
  | 'error'               // { code, message }
```

### 5.4.2 双端收发器（对称实现）

```ts
function createBridge(selfOrigin: string, peerOrigin: string) {
  const pending = new Map<string, Deferred>()

  window.addEventListener('message', (event: MessageEvent) => {
    // ★ 安全三连：origin 白名单 → source 字段 → 消息形状
    if (event.origin !== peerOrigin) return
    const msg = event.data as Envelope
    if (!msg || typeof msg !== 'object' || !msg.source || msg.source === SELF) return
    // 请求-响应关联：带 requestId 且在 pending 表里 → resolve
    if (msg.requestId && pending.has(msg.requestId)) {
      pending.get(msg.requestId)!.resolve(msg.payload)
      pending.delete(msg.requestId)
      return
    }
    dispatch(msg)   // 单向通知走事件分发
  })

  function send<T>(type: MessageType, payload: T, requestId?: string) {
    // ★ targetOrigin 精确指定；parent（3D→宿主）或 contentWindow（宿主→3D）按端选择
    peer.postMessage({ source: SELF, type, payload, requestId,
                       timestamp: Date.now() }, peerOrigin)
  }
  return { send, on: dispatch.on }
}
```

### 5.4.3 协议设计原则

1. **信封自描述**：`source` + `type` + `requestId`，任何一端收到消息先验身份再验形状；
2. **RPC 与通知分流**：需要结果的用 `requestId` 关联（`scene:load` → `scene:loaded`），纯通知不带（`load:progress` 流式上报）；
3. **只传数据**：payload 全部是可结构化克隆的纯数据（URL、坐标、关键帧数组），不传函数/DOM 引用/类实例——postMessage 传不了，也会诱导出错误设计；
4. **大资源不过桥**：全景图、模型文件只传 URL，3D 应用自己 fetch（还能享受 HTTP 缓存与 CDN）；
5. **版本协商**：`ready` 消息带 `version`，宿主发现协议版本不匹配可提示刷新。

## 5.5 安全模型

```ts
// 宿主侧创建 iframe 时的最小权限沙箱
iframe.setAttribute('sandbox', 'allow-scripts allow-same-origin')
// 不给 allow-top-navigation（禁止 3D 应用导航父页面）
// 不给 allow-popups / allow-forms
```

1. **发送端**：`postMessage(msg, peerOrigin)` 永远精确指定 targetOrigin，杜绝 `'*'`（否则 iframe 被嵌到恶意页面时消息外泄）；
2. **接收端**：`event.origin` 白名单校验是唯一可信判据——**不要信任 `event.data.source` 之外的信息**，`source` 字段只是路由提示，防的是误处理不是攻击；
3. **payload 校验**：对关键指令（如 `scene:load`）的 payload 用 Zod 验形状，畸形消息丢弃并上报 `error`；
4. **sandbox 收权**：iframe 不需要表单/弹窗/顶层导航，一律不给；
5. **CSP 兜底**：3D 应用响应头加 `frame-ancestors 'self' https://app.example.com`，限制谁能嵌它。

## 5.6 2D 画布 ↔ 3D 导演台的数据同步

**原则：2D 画布数据是唯一权威源；单向流 + "谁操作谁是写端"仲裁，不做双向自动绑定。**

```
[写向 1] 画布 → 3D（画布是写端）
  用户改分镜/元素/全景图
  → 宿主把变更 diff 成指令序列（scene:load / camera:set ...）
  → postMessage 推给 3D 应用增量更新场景

[写向 2] 3D → 画布（3D 是写端）
  用户在导演台里拖机位、调时间轴
  → 3D 应用在 pointerup/时间轴停止时回传 camera:snapshot
  → 宿主写入 DirectorNodeData.cameraState → 走第 4 章的持久化链路

[防循环]
  画布 → 3D 的更新指令携带 revision 号
  3D 应用对"源自宿主的变更"不再回传 snapshot（回环过滤）
```

镜头数据落地为创作资产：用户在 3D 里调好的机位快照 `cameraState`，可以"绑定到分镜节点"——生视频时该分镜的 prompt 会拼上机位描述（如"低角度仰拍、缓慢推近"），实现 3D 排镜 → 2D 生成的闭环。

## 5.7 性能优化清单

| 问题 | 手段 |
|---|---|
| 首次打开慢 | 隐藏 iframe 预热（5.3）；3D 应用代码分割（首帧只加载渲染核心，模型/后期处理懒加载） |
| 资源加载无反馈 | `load:progress` 流式上报，宿主渲染进度条 |
| 二次打开慢 | 产物文件名带 content hash，CDN 强缓存一年；`ready` 握手命中 < 300ms |
| 3D 掉帧影响感知 | 不可见时（面板折叠）3D 应用暂停 render loop（`setAnimationLoop(null)`），恢复时再启动 |
| WebGL 上下文丢失 | 3D 应用监听 `webglcontextlost/restored`，恢复后重建场景并回放最近一次 scene:load |
| 消息洪泛 | 进度类通知节流（100ms 批量合并）；时间轴回放期间状态回传只发关键帧不逐帧 |

## 5.8 面试考点提炼

1. **"为什么 iframe？"** → 5.1 表格四收益一代价，落点在"低频指令级通信使序列化代价可忽略"；
2. **"postMessage 协议怎么设计？"** → 信封（source/type/requestId）+ RPC 与通知分流 + 只传数据 + 大资源传 URL（5.4）；
3. **"怎么保证安全？"** → 发送端精确 targetOrigin、接收端 origin 白名单、sandbox 最小权限、payload Zod 校验、CSP frame-ancestors（5.5）；
4. **"iframe 慢怎么办？"** → 预热 + 代码分割 + hash 强缓存 + ready 超时降级（5.3/5.7）；
5. **"两边数据怎么不打架？"** → 唯一权威源 + 谁操作谁是写端 + revision 防回环（5.6）；
6. **埋的深挖点**："requestId 超时了怎么办？" → Deferred reject + pending Map 清理，防内存泄漏；"WebGL 上下文丢了？" → 5.7 的 lost/restored 重建策略。
